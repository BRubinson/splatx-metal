# Contributing to splatx-metal

Thanks for your interest in contributing. This document explains what kinds of
contributions are useful, how to build and test, and the source-provenance
rules that every change must follow. The license discipline in §6–§7 is not
bureaucracy — this project's core promise is that it is safe to ship
commercially under Apache-2.0, and that promise is enforced at file
granularity.

## 1. Ways to contribute

You do not need training hardware for many of the most useful contributions:

- **Documentation** — fixes, clarifications, and translations.
- **Pure CPU code** — the COLMAP parser (`.bin`/`.txt`), PLY/SPZ I/O, and
  checkpoint format code have no GPU dependency and are fully covered by the
  C++ test suite.
- **Benchmark reports** — timings and PSNR on chips we have not measured
  (M-series variants, different memory sizes). Open an issue with the exact
  command, machine, and output.
- **Bug reports with reproduction** — a COLMAP dataset shape or CLI flag
  combination that misbehaves is valuable even without a fix.

With an Apple Silicon machine you can additionally work on kernels, the
trainer, and the macOS app. For large features, please open an issue or a
Discussion first so the design can be agreed before you invest the work.

## 2. Prerequisites

- **An Apple Silicon Mac.** Training requires a Metal GPU; there is
  deliberately **no CPU training path** (the CPU backend is a forward-only
  verification oracle, not a fallback).
- **macOS 15+ with a Swift 6.2 toolchain** for CLI/runtime-source work.
- **macOS 26 and Xcode 26** for app work, offline `.metallib` compilation,
  and the complete release gate (Metal 3.2).
- [xcodegen](https://github.com/yonaskolb/XcodeGen), only if you build the
  macOS app.
- **No Apple Developer account is needed.** Every gate below runs unsigned
  (`CODE_SIGNING_ALLOWED=NO`). You only need a team identity to run the
  signed app from Xcode, never to build or test.

## 3. Build and test

Four gates. A PR should state which ones you ran and their results (current
expected counts live in the README and CI, not here — they grow over time):

```sh
# 1. Build + C++ core suite (golden-fixture numerical validation)
swift build
swift run splatx-core-tests

# 2. The same suite against the offline-compiled kernel library.
#    Kernels compile through two paths (runtime source concat and offline
#    per-file .metallib); symbol collisions surface in only one of them,
#    so BOTH must pass for any kernel change.
tools/build_metallib.sh
SPLATX_TEST_METALLIB=build/splatx.metallib swift run splatx-core-tests

# 3. Swift package tests (C-boundary wiring; needs a Metal device)
swift test

# 4. macOS app tests (only needed for app changes)
cd apps/SplatXMetalTrainer && xcodegen generate && \
  xcodebuild test -project SplatXMetalTrainer.xcodeproj -scheme SplatXMetalTrainer \
    -destination 'platform=macOS,arch=arm64' CODE_SIGNING_ALLOWED=NO
```

There is no single-test filter in the core runner; run the suite and grep the
output for your test name. Adding a test is just adding a file with
`SX_TEST(name) { ... }` — registration is automatic.

## 4. Golden fixtures: how correctness works here

This is the part that makes kernel contributions unusually tractable: **you
can verify a kernel change without PyTorch, CUDA, or a gsplat checkout.** All
golden fixtures (212 files, ~2.5 MB) are committed under `fixtures/` as
`.sxt` tensors generated by gsplat's reference implementation at commit
`77ab983`. The full numerical gate runs from a clean clone with `swift run
splatx-core-tests`.

Rules that keep this trustworthy:

- **Tolerances live in each fixture's `meta.json` and nowhere else.** Tests
  must not hardcode tolerances; a missing key is a failure, and an empty
  comparison fails rather than passing vacuously.
- **Never loosen a tolerance to make a test pass.** If a change genuinely
  shifts numerics, the PR must include the measured violation report (the
  test failure prints rtol/atol and worst-index actuals) and the reasoning.
- **New fixtures are regenerated and committed by maintainers** from gsplat
  `77ab983` (`tools/gen_fixtures.py`; requires a local gsplat clone and
  PyTorch). Contributor PRs should include the generator registry change but
  not hand-built `.sxt` binaries — goldens produced by the implementation
  under test would be self-confirming.
- CI never depends on PyTorch; it consumes committed fixtures only.

## 5. Reproduction contracts — read before "fixing" odd behavior

This project is a numerical reproduction of gsplat pinned at commit
`77ab983`. Several behaviors that look like bugs are **deliberate
reproductions**, and the committed goldens enforce them:

- Adam has **no bias correction**, and its epsilon default is `1e-15` (not
  the usual `1e-8`).
- Culled Gaussians (radii ≤ 0) leave their projection outputs **unwritten
  (garbage)** — they must be neither read nor zero-filled.
- The MCMC strategy's Adam-state resets are **asymmetric** between relocation
  and addition (relocate resets sampled source rows only; add resets new rows
  only).

"Fixing" any of these breaks the goldens and will be rejected. Upstream
gsplat is intentionally **not tracked**; matching newer gsplat behavior is a
regression here. The short list of approved deviations from the reference is
documented in [docs/kernel-specs/00-index.md](docs/kernel-specs/00-index.md).
If you believe you have found a genuine bug, open an issue with the fixture
comparison output before writing a fix.

## 6. Source-license discipline (mandatory)

This project is distributed under Apache-2.0, and every line's origin is
tracked. Contributions must follow the same source tiers the project itself
follows:

| Tier | Projects | What is allowed |
|---|---|---|
| Derivation allowed | gsplat, 3dgrut (3DGUT path), ppisp, brush — all Apache-2.0 | Reading and porting code, with the per-file derivation header (§7) and a NOTICE entry |
| Vendoring allowed | spz, MetalSplatter, spz-swift — all MIT | Including source, with license text preserved under `ThirdParty/` |
| Ideas only | msplat, splat-apple, gsplat-mlx | Concepts may be discussed; **this project does not use their code or API signatures**, and contributions must not either |
| Not used at all | OpenSplat (AGPL-3.0), Artifixer weights, 3dgrut's `optix-dev` directory | **This project does not reference these sources in any form.** PRs containing code derived from them cannot be accepted — AGPL derivation is incompatible with this project's Apache-2.0 distribution |

If you are unsure which tier a source you consulted falls into, say so in the
PR — declaring it up front is always acceptable; discovering it later is not.

## 7. Provenance requirements

If your change ports or adapts code from a derivation-allowed source, the
file header must carry exactly two lines, e.g.:

```
// Derived from nerfstudio-project/gsplat (Apache-2.0), commit 77ab983.
// Reimplemented for Metal/C++.
```

Every kernel or math implementation file — **including fully self-authored
ones** — gets one row in the provenance ledger
([docs/provenance.md](docs/provenance.md)): `| file | source repo | commit |
method (ported/reimplemented/original) |`. Self-authored entries are the
negative evidence that a file is *not* a derivation. If your implementation
deviates intentionally from the reference, record the deviation in the
ledger row — otherwise it will be mistaken for a bug in a future comparison
against gsplat.

## 8. Commits and pull requests

- One-line, imperative, English commit subjects (`Fix radix sort histogram
  overflow at N > 4M`). No strict format beyond that; a body explaining *why*
  is welcome for non-obvious changes.
- Keep PRs focused; separate mechanical churn from behavior changes.
- Fill in the PR template — it asks for gate results and the provenance
  declaration (§6–§7).

## 9. AI-assisted contributions

Using AI tools is fine. You are the author of record: you must understand
the change, be able to answer review questions about it, and have actually
run the gates. PRs that show signs of unreviewed generation (fabricated APIs,
tolerance loosening, contract "fixes" from §5) will be closed.

## 10. Review expectations

This project is maintained by a small team. Expect a first review within
**1–2 weeks**; license/provenance questions are resolved before code review.
CODEOWNERS routes kernel, fixture, and provenance changes to maintainers —
those areas have a higher review bar because a mistake there is a
correctness or licensing incident, not a style issue.

## 11. Language

Public documentation is in English. Some deep-dive kernel documents and code
comments originate in Korean and are being translated over time — asking for
clarification in English in Issues/Discussions is always welcome and will be
answered in English.

## 12. How this repository is operated

Day-to-day development happens in a private repository; this public
repository is the **release publication channel**, updated as squashed
release snapshots. Pull requests are received **here**: they are reviewed
here, merged here, and also imported into the private tree so the next
release snapshot contains your change. Your merge commit remains in this
repository's history. Issues and Discussions here are the project's public
tracker of record.
